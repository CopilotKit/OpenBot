# What these tests prove about a shipped app

Every difference between the test setup in this folder (CI on a GitHub macOS runner, iPhone
simulator, iOS 26.5) and a signed App Store build on a real iPhone talking to https://my.open.bot.

- **Real backend**: tested against https://my.open.bot as deployed today (suite 1 in SUMMARY.md).
- **Simulated**: tested here against something that stands in for production (how is said).
- **Not tested here**: why, and what would test it.

| Difference | Status | Evidence or what would test it |
| --- | --- | --- |
| Signing in with Google end to end | Real backend (twice, by hand) | Proven twice on my.open.bot, each run started by hand because every attempt sends a prompt to the account's phone: in the system sheet (run 46097788813) and in the app's web view followed by the whole journey (video run 46110045858), both finishing Google's 2-Step Verification with an authenticator code (TOTP from a secret, CryptoKit). CI on push skips both; the signed-in journey on push runs on a session cookie (Debug hook). |
| Debug vs Release build | Real backend, and simulated | `RealBackendUITests` runs from a **Release** build, a fresh install per test, with no hook. CI fails if a DEBUG hook name is in the Release binary or if its Info.plist has any App Transport Security exception (`Build for testing (Release) and check what ships`). Hooks that need a Debug build (the session-cookie journey, the sheet opened on an arbitrary URL, the mock suite) say so in the summary. `OPENBOT_BASE_URL` and `OPENBOT_SHELL_DIAGNOSTICS` stay readable in Release: a launch environment cannot be set on a person's phone. |
| http vs https, App Transport Security | Real backend | The Release suite talks only to https://my.open.bot with no ATS exception. `NSAllowsLocalNetworking` is added to Debug builds only (`project.yml` build phase), for the http mock and the probe. Run 46092731869 also ran the hand-off flow on a Release build over https through a TLS proxy with a throwaway CA (ATS accepted it with no exception); that proxy was then dropped by decision, so it is no longer re-run. |
| Session cookie name and attributes | Real backend (partly), simulated | Production's cookie is `__Secure-better-auth.session_token`; the app looks for both names and deletes only those two. In run 46092731869 the https mock set the production cookie through the hand-off's `/enter` 303 inside WKWebView: stored as Secure, HttpOnly, SameSite=Lax, persistent, not visible to `document.cookie`, `isSecureContext` true, survived a relaunch of a Release build. On my.open.bot the session-cookie journey (Debug hook) shows the real cookie accepted. The mock suite uses the plain-name cookie over http. |
| Sending a message and the Bot's streamed reply | Real backend | The session-cookie journey (Debug build only because of the cookie hook) sent one real message from Home through the software keyboard; the conversation opened and the Bot's whole reply was on screen within the first 3 s sample, so the increments of the stream were too fast to observe at that rate. |
| Cloudflare in front of production | Real backend, from one kind of client | my.open.bot is behind Cloudflare: a `cf_clearance` cookie for `.open.bot` appears in the web view's store, and no challenge page was ever shown to the runner. That is a GitHub-hosted macOS runner's IP. A phone on a carrier, a corporate network or a VPN is a different client and may get Cloudflare's "Performing security verification" page inside the web view (the Android shell's first real-backend run got one; iOS never has in CI). The app shows such a page as it is: the loading skeleton fades as soon as a finished page shows text even without the bridge's `ready` (8 s at most) (`testSkeletonNeverTrapsAPageWithoutTheBridge`), and the load watchdog never locks a page that has committed. One production run (46102422558) also got a 503 from my.open.bot for a moment. Test with TestFlight on cellular and on a corporate network. |
| The hosted sign-in's real redirects | Real backend | In the web view: `my.open.bot/sign` → `/api/auth/hosted/sign-in` → `dashboard.operations.copilotkit.ai/intelligence/handoff` (the identity provider page: GitHub, Google, Microsoft, email and password) → `accounts.google.com/o/oauth2/auth` → `accounts.google.com/v3/signin/identifier`. Google did **not** refuse the embedded web view: the email and password steps went through in the web view and in the system sheet alike. Both then stopped at Google's 2-Step Verification phone prompt (the account's default second step), so a full Google sign-in was not proven end to end in either. |
| The sign-in hand-off endpoint | Simulated | Not deployed: the probe gets 404 on my.open.bot (every production run), and the app falls back to the web sign-in, as designed. The hand-off itself (sheet, ticket, PKCE verifier, `/enter`, cookie in the web view) is tested against `app/workbench/mock-server.ts` (suite 2). |
| Shell mode and /conversations | Simulated | Not deployed (web draft PR 2360). On production the web app draws its own sidebar toggle inside the tabs, sends no bridge messages, and the Conversations tab shows Home (there is no /conversations page). The shell copes: it notices signing in and signing out from the web view's URL. Suite 2 tests the real thing on this branch's web build. |
| The hand-off's https callback (associated domains) | Not tested here | The app asks `/api/auth/shell/config?platform=ios` and, for `"callback":"https"`, finishes the sheet on `https://my.open.bot/api/auth/shell/callback` (iOS 17.4+ `ASWebAuthenticationSession.Callback.https`). The decision is unit-tested (`HandoffConfigTests`). Whether iOS hands the callback to the app needs a build signed with the team's profile (Team ID still a TODO), the associated-domains entitlement and the association file live on the real domain: none of which a CI simulator build has. Test on TestFlight once the server ships it. |
| The hourly renewal of the hosted sign-in | Not tested here | The app intercepts `/api/auth/hosted/sign-in` while signed in and, when the server has the hand-off, renews in the sheet. Neither the renewal nor the hand-off is on production yet, and an hour is longer than a CI job. Test: deploy the hand-off, sign in on TestFlight, leave the app for over an hour, come back. |
| Signing out | Simulated (mock), real backend (video run) | The web app's own Sign out; the app notices it from the bridge's `signed-out` or the URL landing on `/sign` and deletes the session cookies. The mock now ends its session on sign-out, as a server does. On production the recorded Google journey signs out from the web drawer's account menu (never the session-cookie journey, which would end the secret's session). |
| Code signing, entitlements, associated domains | Not tested here | CI builds with `CODE_SIGNING_ALLOWED=NO` for the simulator. The app needs no entitlement today and registers no URL scheme (the sheet's callback needs none). Test: an archive signed for TestFlight. |
| Push notifications, APNs | Not tested here | Not implemented in the shell; the web app turns web push off inside the shell. Needs a decision and a real device. |
| Microphone and camera prompts | Not tested here | The app grants media capture only to the OpenBot origin; iOS still asks the person. The simulator has no microphone or camera to grant. Test on a device: dictation and a call. |
| Software keyboard | Simulated | The simulator's software keyboard is on in CI (`ConnectHardwareKeyboard` off). Tested: the tab bar hides while it is up; the web view ends at the keyboard's top so the message box and Send stay above it (`testKeyboardKeepsTheMessageBoxVisible`, Home and a conversation); the form-assistant bar is removed (`KeyboardAccessory.swift`, private WebKit class: a future iOS may bring the bar back); a drag down the page closes it, including on a page that does not scroll (the web app turns overscroll off, so a pan recognizer beside WebKit's ends editing after a 40 pt downward drag that did not start in a field); the tab bar comes back with the web view right above it. Real-device feel (third-party keyboards, dictation, the drag's speed under a finger) is not tested. |
| Background suspension, the live socket on resume | Simulated (mock), real backend | `testResumeFromBackground` (mock) and the session-cookie journey (real backend, run 46096038737) send the app to the background for 40 s and check the page still routes. In the real journey the web app's WebSocket to `wss://my.open.bot` opened 7 times and closed twice (code 1005) across sending, the background and the relaunch, and every tab still worked afterwards. A real phone suspends harder and longer (minutes to hours, low power mode): test on TestFlight by leaving the app overnight. |
| WebContent process killed under memory pressure | Simulated | `testWebContentProcessKilledRecovers` kills the page's process with WebKit's private test call (`_killWebContentProcess`, DEBUG hook) and checks the skeleton went up, the page reloaded and the tabs still route. A real kill under memory pressure on a device is not reproduced: test on an older device with many apps open. |
| WebKit storage policies (ITP), the server's 7-day sliding session | Not tested here | WKWebView in an app is not Safari: ITP's 7-day cap on script-writable storage applies to Safari-like browsing, while the session cookie is HttpOnly and set by the server, so it lives as long as the server says (7 days, sliding). A week is longer than CI. Test: TestFlight, do not open the app for 8 days, then open it (expect the native sign-in screen, not a broken page). |
| Lockdown Mode | Not tested here | Lockdown Mode turns off some web features (JIT, some fonts and APIs) in WKWebView too. Test on a device with Lockdown Mode on. |
| MDM, per-app VPN, corporate proxies, private VPC deployments | Not tested here | The lock screen copy names VPC and network settings for this case. Test with a managed device and a deployment reachable only on a private network. |
| iPad, rotation | Simulated | A phone is held to portrait (decision: the web app's phone layout is drawn for portrait, and in landscape the keyboard would leave the message box about 100 pt); `testRotation` checks it stays portrait when the phone turns. An iPad turns every way; the test workflow's `device: ipad` input runs the mock suite and the hardening tests on an iPad simulator, where `testRotation` checks the tab bar and the page follow the turn. Split View and Stage Manager are not tested. |
| Older iOS versions | Not tested here | The deployment target is iOS 17; the runner has only iOS 26.2, 26.4 and 26.5 simulator runtimes (no 17 or 18), and CI runs 26.5. The web view reports `iPhone OS 18_7` in its user agent even on 26.5 (WebKit froze it). Test: TestFlight on an iOS 17 device. |
| Sign-in with the system sheet, consent alert | Simulated, real backend (partly) | The system consent alert ("wants to use … to sign in") and the sheet's page are reachable from XCUITest through the app's own tree. On production the sheet showed the identity provider, Google's page and, in the ephemeral session, iOS's own "Save Password?" prompt. |
| Larger text, dark mode, VoiceOver | Simulated | `HardeningUITests`: the first screen, the lock screen and the tab bar at the largest accessibility text size, light and dark, every control reachable; every native screen in dark; the labels VoiceOver reads on Sign in, Try again, the support link and the three tabs. VoiceOver itself (focus order, gestures) is not driven: test on a device with VoiceOver on. |
| A server that answers slowly or never | Simulated | `testSlowServerShowsSkeletonThenLock`: against a server that takes the connection and never answers, the skeleton covers the wait and the lock screen replaces it at the 20 s load deadline, with no moment showing neither. A slow but working network (pages in 5 to 20 s) shows the skeleton the whole time. |
| A session set seconds before the app is killed | Known limit | Run 46118857052 lost a session cookie set 6 s before the app was killed (SIGKILL, never sent to the background): WebKit writes cookies to disk lazily, and WKHTTPCookieStore has no supported flush. A person whose app is killed within about 6 s of signing in signs in again. Going to the background first is not a guarantee either: 2 later runs (46146892704, 46151172714) lost a cookie set about 8 s before the kill, after 3 and 5 s in the background. The tests now wait 10 s in the background before killing the app (`leaveAndTerminate`). How long WebKit waits before it writes a new cookie to disk is not documented; on a phone, iOS rarely kills an app this soon after it leaves the screen. By decision the session is not mirrored into the Keychain. |
| The request that loads `enter` | Simulated (measured) | `testEnterRequestHeaders` (run 46144561848, iOS 26.5 simulator) loads the probe's `/api/echo-headers` through the exact call `enter` uses (`WKWebView.load(_:)` with `OpenBot-Shell: ios`). From the signed-out first screen and as a renewal with a page showing, WebKit sent the same: `Sec-Fetch-Site: none`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, no `Sec-Fetch-User`, and `OpenBot-Shell: ios`. Other iOS versions not measured. |
| App Review | Not tested here | A web view app needs native value to pass review (guideline 4.2). The native sign-in, tab bar, lock screen and (later) notifications are that value; only a submission tells. |

## Real-device checks for the first TestFlight build

1. Install, sign in with Google (sheet), use all three tabs, send a message and watch the reply stream.
2. Leave the app in the background for an hour and overnight; open it: same page, socket back.
3. Airplane mode on and off: the lock screen, then the app back by itself.
4. On cellular and on a corporate network or VPN: no Cloudflare challenge page in the app.
5. Dictation and a call: the microphone prompt names OpenBot and works.
6. An iOS 17 device, an iPad in both orientations (and Split View), and Lockdown Mode.
7. Do not open the app for 8 days, then open it: the native sign-in screen.
8. VoiceOver on: sign in, move between the tabs, and reach Try again on the lock screen.

## Proven only on a simulator

Everything in suite 2 and the hardening tests runs only on an iOS 26.5 simulator against the mock
stack. These have never run on a real device or against production:

- the sign-in hand-off (sheet, ticket, PKCE, `/enter`) and its https callback;
- the tab bar driving the web app through `openbot:open`, and the bridge's `ready`, `route` and
  `signed-out` (not on my.open.bot yet);
- the keyboard layout and the drag-down dismissal;
- the skeleton timing and the absence of white frames (judged from simulator recordings);
- the lock screen lifting by itself when the network comes back (the network loss is a DEBUG hook,
  not a real radio);
- recovery from a killed web content process;
- the iPad layout, the largest text size and dark mode.
